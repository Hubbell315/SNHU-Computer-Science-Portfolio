The artifact selected for my software design and engineering enhancement is Travlr Getaways. This artifact was a full-stack travel application originally developed for CS 465 in 06/2026. The application includes a public-facing travel site and an Angular single-page administrative application. The technical stack includes Angular on the client side, Node.js and Express for the server-side API, MongoDB for data persistence and JSON Web Tokens for administrator authentication. I decided to use this artifact because it demonstrates a complete application architecture rather than a single isolated program. It allows me to show how a client application, REST API, database model, authentication process and administrative functions work together to deliver a practical solution.

I included Travlr Getaways in my ePortfolio because it demonstrates my ability to work across the full software development process. The original artifact already included the core CRUD functionality for travel trips, an Angular administrative interface, MongoDB persistence and JWT-based login. For this enhancement, I focused on improving the design, maintainability, validation and security of the backend API. I revised the trip model to enforce unique trip codes, trim string values, apply length limits, standardize trip codes to uppercase and record creation and update timestamps. These changes improve data consistency and reduce the chance of invalid or duplicate records being stored in the database. I also improved the trip controllers by creating reusable functions for building validated trip data and returning consistent database error responses. Rather than allowing the API to use the entire request body directly, the enhanced code accepts only expected trip fields. This design reduces the risk of unintended data being inserted into a trip document. The controllers now validate required fields, reject invalid dates, return appropriate HTTP status codes and handle duplicate-key and validation errors without exposing raw database details to the client. The update route now returns the newly updated record and runs Mongoose validators during updates. I also removed debug logging from the original controller implementation. Specifically, `app_api/controllers/trips.js` now uses the `buildTripData`, `validateTripData` and `sendDatabaseError` helper functions to keep request processing consistent. In `app_api/routes/index.js`, the `authenticateJWT` middleware verifies a token before allowing protected requests to reach the trip controllers. Security was a major part of the enhancement. The original JWT middleware called `next()` after beginning token verification, which could allow an invalid token to continue to a protected controller. I replaced that logic with a synchronous verification process inside a `try/catch` block so that the request continues only after the JWT is confirmed as valid. I also protected the delete route, which had previously been available without authentication. Public users can still browse available trips, while only authenticated administrators can create, update, or delete trip records. I tested this change by sending an unauthenticated delete request to the API. The enhanced API returned a 401 Unauthorized response and left the existing trip data unchanged.

This enhancement meets my planned software design and engineering outcome by demonstrating my ability to improve an existing computing solution using industry-relevant tools and practices. The artifact shows full-stack development, API design, database schema design, input validation, error handling and security-conscious authentication. It also contributes to the security outcome because the enhanced design anticipates unauthorized access attempts and protects administrative functions with JWT validation. My outcome coverage plan remains the same: Travlr Getaways is my primary artifact for software design and engineering, while later artifacts will provide stronger coverage for algorithms and database concepts. The enhancement process showed me that a working application is not automatically a well-designed application. The original project functioned correctly for basic travel management, but the code needed stronger validation, more consistent responses and better protection for sensitive administrative actions. One challenge was improving security without breaking the public travel browsing experience. I addressed this by keeping GET trip requests public while requiring authentication only for create, update and delete operations. I also learned that small implementation details, such as where environment variables are loaded or when `next()` is called in authentication middleware, can create important security and reliability problems. Overall, this enhancement improved my ability to evaluate existing code, identify design flaws and make focused changes that improve a working application.
